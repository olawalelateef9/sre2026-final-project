# Build and supply-chain security

How Techbleat Global Bank images are built, checked, published and verified.
The pipeline is [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml).

## Pipeline

| Stage | Runs on | What it does | Fails the run when |
|---|---|---|---|
| Secret scan | every PR and push | gitleaks over the **full git history** | any secret is found |
| Dependency scan | every PR and push | Trivy over the Python and npm lock files (`requirements.txt`, `package-lock.json`). `pom.xml` is skipped because resolving it needs Maven Central, which rate-limits scanners. Java libraries are gated in the image scan, which reads the built JAR. | a fixable HIGH/CRITICAL finding is not in `.trivyignore` |
| Tests | every PR and push | `mvn verify` (transaction), pytest (user, activity), unittest (finance-agent), production frontend build | any test fails |
| Bundle check | every PR and push | gitleaks over the built browser bundle | a secret is compiled into the frontend |
| Image build and scan | every PR and push, after **all** of the above pass | builds each image and scans OS packages and libraries with Trivy | a fixable HIGH/CRITICAL finding is not in `.trivyignore` |
| Publish | push to `main`, `v*.*.*` tags, manual runs | pushes the scanned image to GHCR, then attaches the SBOM, signature and provenance below | any step fails |

Nothing is published unless every earlier stage passes, and an image is scanned
before it is pushed.

## What a published image carries

- **Immutable, traceable tags:** `sha-<full commit SHA>`, plus `<version>` for
  `v*.*.*` tags. There is no `latest`. Deployments reference the **digest**
  (`@sha256:…`) printed in the run summary.
- **OCI labels:** source repository, commit and build time.
- **SBOM:** SPDX JSON generated by Syft. It is saved as a run artifact and
  attached to the image as a signed attestation.
- **Signature:** keyless Cosign signature using the workflow's GitHub OIDC
  identity. There is no signing key to store or leak.
- **Build provenance:** a SLSA provenance attestation from GitHub, linking the
  digest to this repository, workflow and commit.

### Verifying an image

```sh
IMAGE=ghcr.io/olawalelateef9/techbleat-transaction-service@sha256:<digest>

# Signed by this repository's workflow
cosign verify "$IMAGE" \
  --certificate-identity-regexp '^https://github.com/olawalelateef9/sre2026-final-project/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# Build provenance (GitHub CLI)
gh attestation verify "oci://$IMAGE" --repo olawalelateef9/sre2026-final-project

# SBOM attestation
cosign verify-attestation "$IMAGE" --type spdxjson \
  --certificate-identity-regexp '^https://github.com/olawalelateef9/sre2026-final-project/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

## Pinning and reproducibility

| What | How it is pinned |
|---|---|
| Python dependencies | `requirements.in` lists direct dependencies; `requirements.txt` is the generated lock of **every** package with hashes. Installs use `--require-hashes`. |
| Java dependencies | Versions are managed by the Spring Boot 4.1.2 BOM. `dependencyManagement` overrides patched transitive libraries. |
| Frontend dependencies | `package-lock.json`, installed with `npm ci` |
| Base images | Version tag plus `@sha256` digest in every Dockerfile and in `docker-compose.yml` |
| GitHub Actions | Full commit SHA, with the release tag in a comment |
| Scanners | Trivy and gitleaks run from digest-pinned images |

Runtime images apply OS security updates published after the pinned base image
(`apt-get upgrade` and `apk upgrade`). Two builds of the same commit can
therefore differ in OS patch level. The published digest is still immutable,
scanned and signed, and that digest is what gets deployed.

To regenerate a Python lock after editing `requirements.in`:

```sh
pip install pip-tools==7.6.2
pip-compile --generate-hashes --allow-unsafe --strip-extras requirements.in
```

## Container hardening

- All services run as a **non-root numeric UID**: 10001 for the APIs, 101 for
  Nginx. Kubernetes `runAsNonRoot` can therefore verify it.
- Runtime images contain no compilers, build tools or package managers' caches.
  pip's `setuptools` and `wheel` are removed.
- Each image has a `HEALTHCHECK` against its `/health` endpoint.
- The JVM sizes its heap from the container memory limit.
- **Frontend:**
  - Nginx runs unprivileged on port 8080 and doesn't show its version.
  - Every response carries a strict Content-Security-Policy:
    - scripts and styles only from the site's own origin
    - network connections only to that origin and Keycloak
    - the page can't be embedded in frames
  - It also sends `nosniff`, `DENY` framing, `no-referrer` and a restrictive Permissions-Policy.
  - Registration (`POST /user-api/users`) is limited to 5 requests per minute
    per client address.
- `.dockerignore` keeps tests, `.env` files and build output out of images.
- **Local Compose:** data stores and internal APIs bind to `127.0.0.1`. Only the
  frontend (port 3000) is reachable from other machines.

## Vulnerability triage

- **Release threshold:** no HIGH or CRITICAL finding that has a fix available.
  The same gate applies to source dependencies and to built images.
  Findings without a fix are reported but don't block, because there's no
  action to take. They're reviewed when a fix appears.
- **When the gate fails:**
  1. Read the finding in the run's Trivy artifact: package, installed version, fixed version.
  2. **Fix it:** upgrade the dependency or base image. Prefer the fixed version on the
     same release line.
  3. **If it can't be fixed yet, or provably doesn't apply:** add the ID to
     `.trivyignore`. Include the reason, who accepted it, and an `exp:` date no
     more than 30 days ahead. The pull request needs code-owner approval.
- **Target fix times:** CRITICAL within 7 days, HIGH within 30 days.
- **Dependabot** opens weekly update pull requests for pip, Maven, npm, base images
  and Actions. They run through the same gate.

development database password `bankpass` in early commits. It is treated as
compromised and must never be used.

## Credentials

- The pipeline uses only the built-in, short-lived `GITHUB_TOKEN`, scoped per
  job. Workflow default: `contents: read`. The image job adds `packages: write`,
  `id-token: write` and `attestations: write`.
- Signing is keyless through OIDC. There are no registry passwords, signing keys
  or cloud credentials in the repository or in GitHub secrets.
- Pull requests from forks don't receive write permissions and never publish.

## Repository settings to enable

These can't be set from the repository files. Apply them in **GitHub → Settings**:

1. **Branches → Add branch ruleset** for `main`:
   - Require a pull request before merging, with at least one approval and **review from Code Owners**.
   - Require status checks to pass. Select every job of the `CI` workflow.
   - Block force pushes and deletions.
2. **Actions → General → Workflow permissions:** "Read repository contents".
   The workflow requests anything more per job.
3. **Code security:** enable Dependabot alerts, Dependabot security updates,
   and secret scanning with push protection.
4. **Packages**, after the first publish: set each `techbleat-*` package's
   visibility. Keep them private unless the cluster can't authenticate to GHCR.
