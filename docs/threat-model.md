# Threat model: Techbleat Global Bank (deployed environment)

Scope: the AWS environment in [environment-architecture.md](environment-architecture.md),
its delivery pipeline, and its operation. Trust boundaries and data classes are defined
there. Evidence references point to [`docs/evidence/`](evidence) and the test suites.

Method: for each threat named in the brief (plus threats found during the project), list the
attack, the controls in place, how they were verified, and what risk remains.
Likelihood/impact: H/M/L for the residual risk after controls.

## Assets

| Asset | Why it matters |
|---|---|
| Customer credentials and sessions | Account takeover leads to direct financial loss |
| Balances and transactions | Integrity is the bank's core promise |
| Personal data (names, emails) | Privacy and regulatory exposure |
| Identity platform (Keycloak, its admin and signing keys) | Controls every login and token |
| Deployment pipeline and images | Compromise reaches every environment |
| Cloud and operator credentials | Full control of the environment |

## Threats and mitigations

### 1. Account takeover
| | |
|---|---|
| Attack | Password guessing or stuffing, token theft, session replay, phishing a login page |
| Controls | Keycloak brute-force lockout (5 failures, increasing wait up to 15 min); 12-character password policy with history; Authorization Code + PKCE only (no password grant, no implicit); exact redirect URIs; 5-minute access tokens; single-use refresh tokens; HSTS-preloaded domain and a valid certificate; CSP (`script-src 'self'`, `frame-ancestors 'none'`) limits token theft via XSS; the master realm and admin console are not public |
| Verified | Realm config as code ([`keycloak/banking-realm.json`](../keycloak/banking-realm.json)); live: master realm and admin `404` |
| Residual | **M**: no MFA and no email verification (SMTP not configured). Mitigation: enable OTP/WebAuthn and SMTP before real use |

### 2. Broken object-level authorization (BOLA)
| | |
|---|---|
| Attack | Change a user ID in a URL, header or body to read or move another customer's money |
| Controls | Every API takes the user from the validated token (`preferred_username`), never from the request; path and `X-User-Id` mismatches return `403`; the customer directory endpoint was removed (`/users/me`); FinanceAgent tools are bound to the token's user, and the transaction service re-checks |
| Verified | Cross-account tests in all services (A5); live `403`s in [phase 3 evidence](evidence/phase3-live-verification.md) |
| Residual | **L** |

### 3. Privilege escalation
| | |
|---|---|
| Attack | A customer gains transaction or admin rights; a compromised service reaches beyond its role |
| Controls | Roles enforced server-side (`banking-customer`, `banking-transact`, `banking-ai-agent`); token role scope limited to banking roles (`fullScopeAllowed: false`); Istio AuthorizationPolicy per workload identity and path; per-service database roles with minimal grants; Pod Security "restricted", non-root, read-only filesystems, no capabilities; pods cannot reach instance metadata (IMDSv2 hop limit 1); Pod Identity roles bound to one service account each |
| Verified | Role tests (A4); live: transaction-service denied Keycloak's admin API (`403`); [least-privilege review](security/least-privilege-review.md) |
| Residual | **M**: the provisioner's `manage-users` permission can assign any realm role, so a compromised user-service could grant itself `banking-transact`. Mitigation: Keycloak fine-grained admin permissions. Customer self-deposit is allowed **for the demo only** |

### 4. Exposed secrets
| | |
|---|---|
| Attack | Secrets in Git, images, the browser bundle, logs or telemetry |
| Controls | Secrets generated by Terraform into Secrets Manager and delivered by External Secrets or ECS; Kubernetes Secrets encrypted with KMS; identity secrets in a separate prefix that EKS cannot read; operator secrets (DuckDNS, Datadog) as local environment variables, never committed; tokens never logged (`security.audit` logs the reason only); Datadog Agent masks bearer tokens, JWTs and password/secret fields |
| Verified | gitleaks over full history (CI); gitleaks over the built bundle (CI); Trivy secret scan of all five released images: **0**; live log scan; Datadog received `[REDACTED_JWT]` and no forged token ([phase 5 evidence](evidence/phase5-observability.md)) |
| Residual | **L**: an old development DB password (`bankpass`) remains in early git history. It is treated as compromised and never used |

### 5. Supply-chain compromise
| | |
|---|---|
| Attack | A malicious dependency, base image, GitHub Action or registry image |
| Controls | Hash-locked Python dependencies; `npm ci` with a lock file; base images and scanners pinned by digest; GitHub Actions pinned by commit SHA; Trivy gate on fixable HIGH/CRITICAL (dependencies and images); SBOM, keyless Cosign signature and SLSA provenance on every image; deployments reference digests; Dependabot proposes reviewed updates; Argo CD deploys only `main` |
| Verified | CI runs; independent `cosign verify` (and a negative test with a different identity) ([supply-chain.md](security/supply-chain.md)) |
| Residual | **M**: signature verification is not enforced at admission in the cluster. Mitigation: an admission policy (Kyverno or Sigstore policy-controller) requiring our signature |

### 6. Data exfiltration
| | |
|---|---|
| Attack | Reading the databases or cache directly, pulling backups, or leaking data through the AI assistant or telemetry |
| Controls | Data stores private (not publicly accessible; endpoints don't resolve publicly), security groups admit EKS nodes (or only Keycloak) only; TLS required; encrypted at rest; per-service roles; master credentials only in the isolated `banking-admin` namespace; FinanceAgent sends the model only type, amount and date (no references or IDs), and is disabled in this environment; telemetry scrubbed |
| Verified | External scan: only 80/443 open; RDS `PubliclyAccessible=False`; restore drill confirmed the restored copy is private and encrypted |
| Residual | **M**: egress from the mesh is `ALLOW_ANY` (needed for AWS APIs). Mitigation: `REGISTRY_ONLY` with explicit ServiceEntries |

### 7. Denial of service
| | |
|---|---|
| Attack | Request floods, expensive endpoints, sign-up abuse |
| Controls | AWS Shield Standard on the NLB; gateway rate limit (local token bucket); per-client sign-up limit in nginx (5/min, real client IP preserved); Keycloak lockout; resource limits on every pod; WAF blocks common attack payloads |
| Verified | WAF `403` on SQLi/XSS probes; rate-limit configuration in [waf.yaml](../deploy/platform/policy/waf.yaml) |
| Residual | **M**: no CDN or global edge (DuckDNS cannot use Cloudflare); limits are per gateway replica |

### 8. Loss of availability
| | |
|---|---|
| Attack / failure | Node, AZ, data-service or deployment failure |
| Controls | Two AZs for nodes; rolling updates (zero-downtime release and rollback measured); Argo CD self-heal; health probes; 7-day point-in-time backups with a rehearsed restore (RTO 12 min); Datadog monitors, an availability SLO and burn-rate alerting; runbook per alert |
| Verified | Rollback in 17 s with 0 errors; restore drill; alert exercise |
| Residual | **M**: single-AZ RDS and Valkey, single NAT gateway, single Kafka broker and Keycloak task (sandbox cost). Mitigation: Multi-AZ RDS, Valkey replicas, NAT per AZ, 3-broker Kafka, 2+ Keycloak tasks |

### 9. Dangling DNS / subdomain takeover (found during the project)
| | |
|---|---|
| Attack | After an environment is destroyed, the domain still points to an IP that AWS reassigns to another customer, who can serve content and obtain a certificate for the domain |
| Observed | Before the first deployment, the domain resolved to a recycled AWS IP, and a stranger's server answered cert-manager's validation request (`404`) |
| Controls | `down.sh` clears the DuckDNS record at every teardown; `up.sh` sets it to the new load balancer |
| Residual | **L** |

### 10. Unreviewed changes and misconfiguration
| | |
|---|---|
| Attack / failure | Manual `kubectl` changes, configuration drift, a bad release |
| Controls | GitOps: only `main` deploys; self-heal reverts drift; two Argo CD projects (the app project cannot change cluster-scoped resources); retries; CODEOWNERS; branch protection (repository setting) |
| Verified | Deleted a security policy and scaled a deployment by hand; both restored in 7 s |
| Residual | **M**: branch protection is a manual repository setting. It must be enabled in GitHub |

## Components of the target architecture not implemented

| Component | Status |
|---|---|
| Cloudflare edge | Replaced by an equivalent (see the environment deviations) |
| Backstage | Not implemented (outside the security scope) |
| Managed Kafka | Replaced by hardened in-cluster Strimzi |
| Banking MCP | Not implemented; FinanceAgent is disabled in the deployment |

## Residual risk summary

| Risk | Level | Owner action before real customer data |
|---|---|---|
| No MFA, no email verification | M | Enable OTP/WebAuthn and SMTP in the realm |
| Provisioner can assign any role | M | Keycloak fine-grained admin permissions |
| Image signatures not enforced at admission | M | Sigstore policy-controller or Kyverno |
| Open mesh egress | M | `REGISTRY_ONLY` and ServiceEntries |
| Single-AZ data services, single broker and IdP task | M | Multi-AZ / replicas |
| No CDN edge | M | A domain on Cloudflare (or AWS CloudFront + WAF) |
| Self-deposit enabled | M (demo) | Restrict deposits to a back-office role |
| Old dev password in git history | L | Treated as compromised; never reused |
